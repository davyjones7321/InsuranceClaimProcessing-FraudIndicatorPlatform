# Baseline Reproduction Report: Findings F1 to F13

This report records the independent reproduction and verification of defects F1 through F13 identified during the baseline audit of base commit `3d49effc6c1a5e3e871447ffa671ebccc08d325a`.

| Finding ID | Finding Description | Status | Evidence Type | Exact Code / Execution Evidence |
|---|---|---|---|---|
| F1 | Application DB role `app_rw` can `UPDATE` and `DELETE` rows in `audit_log`, `claim_status_history`, `decisions`, etc. The `REVOKE` in `deploy/init-db.sql` is commented out and Alembic migrations have no triggers or grants. | Reproduced | Reproduced via execution & code inspection | `deploy/init-db.sql` lines 20-21 explicitly executes `ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_rw;`. Line 28 has `-- REVOKE UPDATE, DELETE ON audit_log...` commented out. Reproduced via `docs/evidence/baseline/reproduce_f1.py` showing in-place row mutation and deletion succeeding without error. |
| F2 | Audit writer races on first write to a new chain and under concurrent load. No concurrency test exists. | Reproduced | Reproduced via execution & code inspection | `app/audit/writer.py` lines 160-176 attempts `SELECT ... FOR UPDATE` on `AuditChainHead`. For a new chain key, this returns NULL for all concurrent transactions, causing each thread to enter `if not chain_head:` and attempt `db.add(chain_head)`. Reproduced via `docs/evidence/baseline/reproduce_f2.py`: 10 concurrent first-writes resulted in 1 success and 9 concurrency collisions/failures. |
| F3 | Claim-scoped mutations do not call `check_claim_access`: `make_decision`, `create_assessment`, `review_document`, `transition_status`, and all investigation mutations. Only reads do. | Read | Read (Code Inspection) | In `app/api/claims.py`, `check_claim_access` is called in only 3 endpoints: line 182 (`get_claim_by_id`), line 213 (`get_claim_history`), and line 317 (`list_claim_documents`). All mutation endpoints (`POST /api/claims/{id}/decisions`, `POST /api/claims/{id}/assessments`, `POST /api/claims/{id}/documents/{doc_id}/review`, `POST /api/claims/{id}/transition`, and all `/investigations/*` endpoints) lack `check_claim_access`. |
| F4 | Customers and staff can read risk evaluations. `tests/integration/test_risk_service.py` asserts that customers can read them. | Read | Read (Code Inspection) | In `app/api/claims.py` lines 529-536 and lines 559-566, `list_risk_evaluations` and `get_latest_risk_evaluation` allow `UserRole.CUSTOMER` and `UserRole.STAFF` in `require_roles`. In `tests/integration/test_risk_service.py` lines 260-272, the test explicitly asserts `resp = client.get(f"/api/claims/{claim.id}/risk-evaluations", headers=cust_headers)` returns status 200 for customers. |
| F5 | `decision_service.make_decision` reads coverage without a row lock, increments `consumed_amount` in Python, never checks remaining limit at approval, silently skips the ledger if no coverage row exists, and has no reversal path. No claim row lock in the decision path. | Read | Read (Code Inspection) | In `app/services/decision_service.py` lines 163-179, coverage is selected via `select(Coverage).where(...)` without `with_for_update()`. Line 169 performs in-memory Python addition `coverage.consumed_amount += payload.approved_amount` without checking against `coverage.limit_amount`. If `coverage` is None, lines 168-179 skip `CoverageLedger` insertion silently. No reversal entry type or reopen method exists. |
| F6 | `claim_limit_policy` is hard-coded to `CAP_WITH_WARNING` in `app/engine/validation.py` and `ruleset_v1.yaml` without an owner decision. | Read | Read (Code Inspection) | In `app/rules/ruleset_v1.yaml` line 6: `claim_limit_policy: "CAP_WITH_WARNING"`. In `app/engine/validation.py` line 34: `limit_policy: str = val_input.ruleset.get("claim_limit_policy", "CAP_WITH_WARNING")`. Hard-coded fallback default was implemented without owner sign-off. |
| F7 | `scripts/replay.py` rebuilds inputs from current database tables, not from stored `inputs_snapshot`. Later data changes cause false mismatches or hide differences. | Read | Read (Code Inspection) | In `scripts/replay.py` lines 32-36, `replay_validation_run` calls `service.build_validation_input(claim=claim, ...)` querying current live tables. In lines 102-106, `replay_risk_evaluation` calls `service.build_risk_input(claim=claim, ...)`. Neither reads from a sealed `inputs_snapshot` field. |
| F8 | Document review does not trigger revalidation. Two different sensitive-document lists exist (`claim_service.SENSITIVE_DOC_CODES` vs inline tuple in `app/security/rbac.py`). Upload does `await file.read()` before the size check. | Read | Read (Code Inspection) | In `app/services/claim_service.py` lines 320-334, `review_document` updates status and audit log but never triggers validation. `claim_service.py` line 35 defines `SENSITIVE_DOC_CODES = {"DOC-GOV-ID", "DOC-DISCHARGE", "DOC-LAB-REPORT", "DOC-DEATH-CERT"}` while `app/security/rbac.py` lines 108-113 checks against `("MEDICAL_REPORT", "DEATH_CERTIFICATE", "IDENTITY_PROOF", "FIR_REPORT")`. In `app/api/claims.py` line 264, upload does `content = await file.read()` before passing to service for size validation. |
| F9 | Audit serializer is a denylist of field names; arbitrary keys and free text pass. Document review remarks go into audit event data. | Read | Read (Code Inspection) | In `app/audit/writer.py` lines 58-74, `_sanitize_and_filter_event_data` inspects keys against `DISALLOWED_SENSITIVE_FIELDS` (denylist). Arbitrary unlisted keys and text pass through. In `app/services/claim_service.py` line 330, `review_remarks` is directly included in `event_data`. |
| F10 | `tests/conftest.py` hardcodes in-memory SQLite. CI starts PostgreSQL but only runs migrations on it. The backup drill can fall back to SQLite or a seeded temporary database. No coverage threshold (`--cov-fail-under`) is enforced. | Read | Read (Code Inspection) | In `tests/conftest.py` line 25, `TEST_DATABASE_URL = "sqlite:///:memory:"` is hardcoded for test runs. In `.github/workflows/ci.yml` line 91, `pytest` runs without `--cov-fail-under`. In `scripts/drill_backup_restore.py` lines 104-109, failed PostgreSQL database creation falls back silently to `sqlite:///{drill_db_file}`. |
| F11 | Missing operational and governance tooling: `scripts/backtest.py`, `scripts/retention_report.py`, external audit anchor export, scheduler, Jinja2 UI templates, production deployment artifacts. | Read | Read (Filesystem Check) | Filesystem checks confirm absence of `scripts/backtest.py`, `scripts/retention_report.py`, templates directory, production compose/manifests, and external anchor export scripts. |
| F12 | A claim whose indicators are mostly skipped can score 0 and look LOW. MEDIUM and HIGH route identically because the investigation threshold equals the MEDIUM lower bound (25), and R05 (weight 25) routes to investigation alone. | Read | Read (Code Inspection) | In `app/engine/risk.py` lines 509-524, unassessed/skipped claims sum to score 0, falling into `RiskCategoryEnum.LOW`. `investigation_threshold` is set to 25, while `low_max` is 24 and `medium_max` is 49. Thus all MEDIUM (25-49) and HIGH (50-100) claims trigger `requires_investigation = True`. In `app/rules/ruleset_v1.yaml` lines 97-101, indicator R05 has weight 25, triggering investigation alone. |
| F13 | Phase reports in `decisions.tsv` claim 14/14 acceptance items and "append-only audit" although F1, F2 and F5 hold. | Read | Read (Code Inspection) | In `decisions.tsv`, phase-8 log claims "all 137 tests pass, coverage 88% overall, 14/14 checklist items passed" and phase-1 claims "append-only audit" despite the lack of database-level immutability (F1), concurrency safety (F2), and coverage lock / ledger atomicity (F5). |
